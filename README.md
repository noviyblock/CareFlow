# CareFlow

**Адаптивная мультиагентная система эмоциональной поддержки: маршрутизация, дистилляция и борьба с sycophancy**

## Описание проекта

Рассматривается задача построения вычислительно эффективной мультиагентной системы эмоциональной поддержки, способной учитывать многотуровую динамику эмоционального состояния пользователя, выбирать между различными стратегиями ответа и не скатываться в sycophancy — чрезмерное согласие с пользователем, которое может выглядеть поддерживающим, но быть нежелательным по содержанию.

Необходимо исследовать адаптивную маршрутизацию между агентами анализа контекста, генерации ответа, проверки безопасности и оценки эмпатии, а также дистилляцию решений полной мультиагентной системы в компактный маршрутизатор или single-agent модель. Отдельно требуется разработать протокол оценки скорости получения ответа и его качества: эмпатии, уместности, навязчивости и sycophancy.

- **Датасеты:** ESConv, EmpatheticDialogues, TIDE, EmoCare, KardiaBench, TEA-Bench, HEART, MoodBench, плюс небольшая тестовая выборка синтетических сценариев эмоциональной эскалации и конфликтующих убеждений.
- **Бейзлайны:** single-agent prompting, ReAct, фиксированная схема planner–generator–critic, multi-agent debate, LLM-as-a-judge, embedding-based response reranking, rule-based и DeBERTa-based sycophancy detectors, response-level и process-level distillation, специализированные подходы (EmoDistill, EvoEmo и т.п.).
- **Требования:** курсы по машинному обучению; bash, git, python, numpy, pandas, pytorch, LLM.
- **Ожидаемые результаты:** пайплайны обучения и инференса; сравнительный анализ по точности и latency; научная статья для подачи на A*-конференцию.

## Постановка задачи

На шаге диалога *t* у системы есть история *h_t* и память о прошлых сессиях *m*. Агенты: анализ контекста, генерация ответа, проверка безопасности, оценка эмпатии/sycophancy. Каждый агент может работать на лёгкой модели (SLM, 0.5–3B) или на тяжёлой (14–32B). Обе работают локально; API — опция только для judge, если локальный не пройдёт валидацию. Роутер π(*h_t*, *m*) решает, какие агенты вызвать и на какой модели.

> максимизировать качество *Q* (измерения HEART, снижение эмоциональной интенсивности)
> при ограничениях: sycophancy ≤ ε, нарушения безопасности = 0,
> минимизировать стоимость *C* (задержка, токены).

Итог — Pareto-фронт «качество против стоимости». Вторая часть — **дистилляция**: перенести решения полной системы в компактный роутер или single-agent модель, которая работает локально и остаётся на фронте.

Вычисления — **локально** (MacBook Pro M5 Pro, 48 ГБ): открытые веса с фиксированной ревизией, задержка меряется без сетевого шума. API подключаем только если локальный judge не пройдёт валидацию на этапе 3.

Ключевые развилки:
- **После этапа 3:** если локальный judge плохо согласуется с людьми, judge (и только он) переходит на API.
- **После этапа 7:** если oracle gate почти не обгоняет лучший одиночный путь (selection effect), фокус статьи смещается с роутеров (этап 8) на дистилляцию (этап 9).
- **Найдено на этапе 2/4:** готовый классификатор эмоций — слабый прокси состояния пользователя (ρ = 0.06 с самоотчётом, см. `docs/data.md`). Детектор по траектории на этапе 5 строим на более точном сигнале.

## Что проверяем

| # | Вопрос | Гипотеза | Как проверяем |
|---|---|---|---|
| RQ1 | Окупается ли маршрутизация в ESC? | Между лучшим одиночным путём и oracle gate есть заметный зазор по качеству при той же стоимости. Альтернатива — selection effect: при сильном энкодере каскад не нужен | Oracle gate vs энкодер vs гибрид на ESConv |
| RQ2 | Какой роутер лучше? | Геометрический отказ (GCUL) и калибровка против overtrust (TAD-CL) лучше порога по confidence; их комбинация с SATER лучше каждого по отдельности | ToGR, ECE, bypass rate, AGL/AROL |
| RQ3 | Помогает ли эмоциональная динамика как сигнал роутера? | Признаки переходов/persistence из Empath улучшают решения о маршрутизации по сравнению с уверенностью на одной реплике | Абляция признаков роутера |
| RQ4 | Как детектировать sycophancy? | Детектор по аномальной траектории эмоций ловит случаи, которые пропускают rule-based и DeBERTa-детекторы | Синтетика с золотыми метками + adversarial-кейсы HEART |
| RQ5 | Какая топология лучше? | Адаптивный выбор агентов не хуже star (InsideOut) и roundtable (UniESC) по качеству при меньшей стоимости | Pareto-фронт качество/latency |
| RQ6 | Сколько качества сохраняет дистилляция? | Компактная модель сохраняет большую часть качества учителя при кратно меньшей задержке | Сравнение со студентами и UniChat |
| RQ7 | Когда помогает память? | Память помогает в диалогах со стабильным состоянием и мало помогает при резкой эскалации (по ACERT) | Сравнение на двух группах диалогов |

Результаты по всем вопросам **ещё не получены**; статус — в таблице плана выше.

## Научная новизна (претензии, требующие подтверждения)

1. Маршрутизация с учётом стоимости **на уровне агентов** для генеративной поддержки, где нет золотого ответа: метку «дешёвый путь справился» задаёт judge по HEART.
2. **Эмоциональная динамика как вход роутера** вместо уверенности на одной реплике.
3. **Sycophancy как аномалия траектории** эмоций + тестовый набор эскалаций и конфликтующих убеждений.
4. Проверка **headroom маршрутизации** в ESC через oracle gate (отрицательный результат тоже является вкладом).
5. **Дистилляция MAS в CLS-роутер** для текстового диалога.
6. **Единый протокол оценки**: качество, динамика, sycophancy, навязчивость, latency.

Не являются новизной: память между сессиями (PAIR, H2HTalk) и сами роутеры GCUL/SATER/TAD-CL — это адаптируемые компоненты.

## Установка (macOS, Apple Silicon)

```bash
brew install uv
uv python install 3.12
uv sync --extra dev --extra api        # + --extra mlx для локальных 7B–32B
```

### DagsHub (MLflow + DVC remote)

Репозиторий `noviyblock/CareFlow` приватный. Все ключи берутся из DagsHub (Settings → Tokens и вкладка Remote → S3) и хранятся только в `.env`, который не попадает в git.

```bash
cp .env.example .env                    # заполнить MLFLOW_TRACKING_* и S3_*
set -a; source .env; set +a
# DVC remote origin = s3://dvc @ https://dagshub.com/noviyblock/CareFlow.s3 (уже в .dvc/config)
uv run dvc remote modify --local origin access_key_id "$S3_ACSESS_KEY_ID"
uv run dvc remote modify --local origin secret_access_key "$S3_SECRET_ACSESS_KEY"   # → .dvc/config.local (не в git)
```

MLflow по умолчанию пишет в `https://dagshub.com/noviyblock/CareFlow.mlflow` (`configs/base.yaml`). Если переменные `MLFLOW_TRACKING_USERNAME`/`MLFLOW_TRACKING_PASSWORD` не заданы, запуск падает сразу. Для офлайн-запуска: `mlflow.tracking_uri=sqlite:///mlflow.db`.

`uv.lock` фиксирует все транзитивные зависимости. Коммитим его вместе с кодом.

## Запуск

```bash
set -a; source .env; set +a              # перед каждой сессией
uv run python scripts/run_experiment.py --config configs/experiments/smoke.yaml
uv run python scripts/run_experiment.py --config configs/experiments/smoke.yaml seed=1
uv run mlflow ui --backend-store-uri sqlite:///mlflow.db   # только для офлайн-прогонов
uv run pytest
```

Каждый запуск логирует в MLflow полный resolved-конфиг, git commit (с пометкой `-dirty`), `dvc.lock` и список версий пакетов.

## Воспроизводимость

- Seed задаётся в конфиге (`seed`), CLI-override `seed=N`. На MPS часть ядер недетерминирована, поэтому отчитываемся mean ± std по ≥3 сидам. Побитовая воспроизводимость гарантирована только на CPU.
- Ответы API-моделей не детерминированы даже при temperature 0. Все вызовы идут через `careflow.cache.LLMCache`. Для повторного прогона ставим `cache.mode=read_only`: ответы берутся из кэша, а промах кэша роняет запуск.
- Секреты (ключи API) передаются только через переменные окружения, имена которых указаны в `configs/compute/*.yaml`.
