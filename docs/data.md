# Данные

Пайплайн: `uv run dvc repro` (стадии `download_*` → `prepare_*`), источники и sha256 в `configs/data.yaml`, результат в `data/processed/<dataset>/{train,valid,test}.jsonl` + `stats.json`. Схема: `src/careflow/data/schema.py`.

## ESConv

- Источник: HF `thu-coai/esconv`, ревизия `32c54c15`, CC BY-NC 4.0.
- **1300 диалогов** (в статье ACL 2021 — 1053; это расширенный релиз). 38 365 реплик, в среднем 29.5 на диалог, максимум 120.
- Сплит: официальный thu-coai 70/15/15 → 910 / 195 / 195. Принадлежность восстановлена по содержимому, совпали все 1300, пересечений нет.
- Стратегии supporter: 8 классов Helping Skills, сильный дисбаланс (Question 3801 … Restatement 1089).
- Оценки seeker по ходу диалога (`feedback`, 1–5): 7681 оценка; в **166 диалогах** есть оценка ≤ 2.

### ⚠️ Финальная интенсивность не даёт контраста

- У 150 диалогов нет `final_intensity`.
- У всех остальных 1150 **интенсивность снизилась минимум на 1** (Δ=1: 417, 2: 433, 3: 193, 4: 107). Релиз, по-видимому, отфильтрован по успешным диалогам.
- Следствие: `initial − final` нельзя использовать как метку «поддержка не сработала» и как контраст для детектора аномальной динамики. Контраст берём из (а) оценок `feedback` ≤ 2 по ходу диалога, (б) синтетических сценариев эскалации, (в) adversarial-кейсов HEART.
- Также: если «нормальная» траектория в ESConv — всегда снижение, то детектор «слишком быстрого перехода к позитиву» нужно калибровать по *скорости* снижения, а не по факту.

## EmpatheticDialogues

- Источник: архив Meta `empatheticdialogues.tar.gz`, CC BY-NC 4.0.
- **24 850 диалогов**, 107 220 реплик, 4.3 реплики на диалог (максимум 8), 32 эмоции.
- Сплит: оригинальный 19 533 / 2 770 / 2 547.
- Особенность формата: запятые в тексте экранированы как `_comma_`; в valid/test ~половина строк имеет 9-е поле без заголовка (кандидаты ответов) — отбрасываем, как ParlAI.
- Роль seeker = автор ситуации (первая реплика). Диалоги короткие: для многотуровой динамики годятся слабо, используем для сравнения с InsideOut.

## Эксперимент `esconv_dynamics` (2026-10-20)

Run: [MLflow](https://dagshub.com/noviyblock/CareFlow.mlflow/#/experiments/1/runs/f4ca0ae1721c4756b81a5cb9daf81247), конфиг `configs/experiments/esconv_dynamics.yaml`. Классификатор `j-hartmann/emotion-english-distilroberta-base` (Ekman + neutral) по 19 990 репликам seeker, все сплиты ESConv. Анализ описательный (exploratory), поправок на множественные сравнения нет.

| Метрика | Значение |
|---|---|
| Доля меток: neutral / sadness / joy / fear / surprise / anger / disgust | 0.39 / 0.21 / 0.18 / 0.07 / 0.06 / 0.05 / 0.04 |
| Средняя уверенность классификатора | 0.74 |
| De-escalation (полярность в конце выше, чем в начале) | 0.65 |
| Escalation | 0.09 |
| «Too fast» (neg → pos за 1 реплику) / «stuck» (3 последние neg) | 0.053 / 0.008 |
| **Proxy validity:** Spearman ρ(Δполярности, Δсамоотчёта интенсивности), n=1150 | **0.06** (p=0.04) |
| Самая длинная серия neg: диалоги с feedback ≤ 2 (n=166) vs остальные (n=1134) | 3.11 vs 2.82, Mann–Whitney p=0.038 |
| «Stuck»: feedback ≤ 2 vs остальные | 0.018 vs 0.006 |

**Выводы:**
1. **Готовый классификатор эмоций по репликам — слабый прокси состояния пользователя.** Его изменение почти не связано с тем, что пользователи сами сообщают об интенсивности (ρ = 0.06). Ограничения сравнения: самоотчёт имеет суженный диапазон (Δ ≥ 1 везде), полярность грубая (−1/0/1). Тем не менее детектор sycophancy «по аномальной динамике» на этом сигнале строить нельзя: нужен более точный сигнал состояния (регрессия интенсивности, appraisal через LLM или модель, дообученная на оценках `feedback`).
2. **Слабый, но значимый контраст:** в диалогах с низкой оценкой пользователь дольше остаётся в негативе, и «застревание» там в 3 раза чаще. Это в пользу гипотезы RQ4, но эффект мал, тест один и не скорректирован.
3. ~~Возможный артефакт (не проверено)~~ → проверено, см. диагностику ниже.

### Диагностика слабого прокси (2026-10-20, ad hoc, по сохранённым предсказаниям; в MLflow пока не оформлено)

| Проверка | Результат |
|---|---|
| Последняя реплика seeker: доля joy / доля прощальных фраз («thank», «bye», «take care»…) | 0.55 / 0.65 (joy среди прощаний — 0.68) |
| Первая реплика seeker: доля neutral | 0.45 (типично «Hello», «Hi», «Yes») |
| ρ(Δ, самоотчёт) — исходная метрика (последняя − первая реплика) | 0.063 (p = 0.035) |
| ρ — без прощаний и реплик < 4 слов, среднее по 3 репликам в начале и конце (n = 1131) | 0.054 (p = 0.067) |
| ρ(доля негатива в первых 3 репликах, начальная интенсивность) | 0.127 (p < 0.001) |

Выводы:
- **Наша метрика была методически слабой:** «конец − начало» по сути измеряла ритуал «привет → спасибо, пока».
- **Но исправление метрики не помогло** (0.054), значит дело не только в ней: сам классификатор слабо отражает интенсивность.
- Классификатор что-то улавливает (ρ = 0.13 с начальной интенсивностью), но слабо: он предсказывает категорию эмоции, а не её силу; проблемы в ESConv часто описываются нейтральным повествовательным тоном.
- Потолок со стороны данных: самоотчёт грубый (1–5), а Δ в узком диапазоне 1–4 (релиз отфильтрован), это занижает любую корреляцию.
- Решение: для оценки состояния нужен другой сигнал (оценка интенсивности по каждой реплике локальной LLM или регрессор, обученный на ESConv), с валидацией против начальной интенсивности и `feedback`.

## HEART (релиз GitHub `Hippocratic-AI-Research/HEART`, коммит `c3387b43`, Apache-2.0)

- Выложено: 280 обычных + 20 adversarial контекстов, по 3 человеческих ответа на контекст, ответы ~20 моделей (в т.ч. frontier), промпты трёх judge (gpt-4o, claude-sonnet-4, gemini-2.5-flash).
- **Не выложено: человеческие попарные оценки** (в статье — 42 000 сравнений, 15 оценщиков). Поэтому напрямую проверить наш judge на людях HEART нельзя.
- ⚠️ **HEART построен на ESConv.** 240 из 300 контекстов делят с ESConv ≥ 2 длинные (> 40 символов) реплики: 166 — с train, 34 — с valid, 40 — с test (107 из них — дословный префикс диалога ESConv).
- **Правило против утечки:** при оценке на HEART исключаем (или отчитываемся отдельно по) контекстам, пересекающимся с ESConv train, если система/роутер/студент обучались на ESConv train. Скрипт проверки пересечения — в этапе 3/4.

## Эксперимент `proxy_validity` (2026-10-20)

Вопрос: виновата наша грубая метрика или классификаторы реплик в принципе не измеряют интенсивность? Run: [MLflow](https://dagshub.com/noviyblock/CareFlow.mlflow/#/experiments/1/runs/4f3b56bdab004f8581dd86ba603b14be), конфиг `configs/experiments/proxy_validity.yaml`.
Метод: непрерывная оценка негатива (сумма вероятностей негативных эмоций), окна по 3 содержательные реплики seeker (≥ 4 слов, без приветствий и прощаний) в начале и конце, Spearman ρ с самоотчётом, 95% бутстрэп-CI (1000). Обучения нет, все сплиты — только валидация.

| Сигнал | ρ с начальной интенсивностью (n = 1273) | ρ с финальной (n = 1131) | ρ изменения (n = 1131) |
|---|---|---|---|
| Ekman DistilRoBERTa (Hartmann 2022) | 0.128 [0.068, 0.183] | 0.079 [0.024, 0.137] | 0.058 [0.000, 0.116] |
| GoEmotions RoBERTa (Demszky et al. 2020) | 0.098 [0.041, 0.156] | 0.101 [0.049, 0.163] | 0.045 [−0.010, 0.111] |
| *подмножество из 400 диалогов (одинаковое для всех строк ниже):* | | | |
| Ekman, подмножество | 0.107 [0.016, 0.210] | 0.074 [−0.028, 0.176] | 0.096 [−0.005, 0.198] |
| GoEmotions, подмножество | 0.066 [−0.028, 0.167] | 0.117 [0.013, 0.222] | 0.054 [−0.056, 0.157] |
| **LLM-оценка 1–5 (Gemma-4-26B-A4B), подмножество** | **0.244 [0.148, 0.342]** | 0.101 [0.001, 0.200] | 0.050 [−0.053, 0.157] |

LLM-прогон: [MLflow](https://dagshub.com/noviyblock/CareFlow.mlflow/#/experiments/1/runs/05ee1a3b00454f6b8818b35f57343c8e), 0% нераспознанных ответов, ~0.3 с на диалог. **Предварительно:** LLM примерно вдвое лучше классификаторов отражает *текущее* состояние (начальная интенсивность), но изменение по ходу диалога не отражает ни один сигнал. Интервалы частично пересекаются — парный бутстрэп разницы (`paired.*`) в очереди.

**Вывод (отрицательный, обоснованный):** два классификатора с разными таксономиями (7 и 28 классов), непрерывная оценка вместо округления и окна без ритуальных реплик дают одинаково слабую связь с самоотчётом: верхняя граница CI ≤ 0.18 для всех трёх проверок, т.е. ≤ ~3% общей ранговой дисперсии. Значит, причина не в нашей метрике, а в самом подходе «классификатор эмоции по реплике → состояние пользователя». Строить на таком сигнале детектор sycophancy по динамике (RQ4) или признаки роутера (RQ3) нельзя.
Оговорка: часть слабости — потолок данных (5-балльный самоотчёт, Δ в диапазоне 1–4), поэтому сравнение сигналов между собой корректнее, чем абсолютные значения ρ. Ключевая проверка — даст ли LLM-оценка заметно больший ρ на том же подмножестве (classifiers: `*_subset.*`).

## Эксперимент `judge_validation` (E2, 2026-10-29)

Run: [MLflow](https://dagshub.com/noviyblock/CareFlow.mlflow/#/experiments/2/runs/5cedd2be5a724b21a01d1339dc9cc23c) (пересчёт из кэша исправленным парсером; исходный прогон `judge_validation` — те же ответы судьи). Judge: Gemma-4-26B-A4B (MLX 4-bit), рубрика HEART. 60 контекстов HEART, 450 попарных сравнений из 15 моделей + человек, 25% пар оценены в обоих порядках.

| Критерий (задан заранее) | Порог | Результат |
|---|---|---|
| Kendall τ с опубликованным рейтингом HEART (15 моделей), 95% CI по контекстам | CI не включает 0 | **0.66 [0.43, 0.75]** ✅ |
| Устойчивость к перестановке ответов | ≥ 0.8 | **0.91** ✅ |
| Нераспознанные ответы (overall) | < 5% | **0.4%** ✅ (было 10.4% со строгим парсером) |

**Вывод:** локальный judge воспроизводит рейтинг frontier-судей HEART и почти не зависит от порядка ответов → **API для judge не нужен**, используем Gemma-4-26B-A4B. Ограничение: эталон — рейтинг, полученный другими LLM-судьями (человеческие попарные оценки HEART не опубликованы), так что это согласие с судьями HEART, а не напрямую с людьми.
Дополнительно: человеческий ответ выигрывает у моделей в 23% сравнений (в HEART — 35.8% по человеческим оценкам; разные выборки пар и судьи, сравнивать напрямую нельзя).
Исправление парсера: в 9% ответов ломалась одна второстепенная категория («A0493» без силы, опечатка «A04493»), при этом общий вердикт был корректен; теперь такая категория не засчитывается никому, а сравнение не теряется.
